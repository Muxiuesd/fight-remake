## 二、分层与依赖方向

```
lwjgl3/Lwjgl3Launcher
  └ ttk.muxiuesd.FightCore            单例 ApplicationListener，持有 3 个 Screen
       ├ game.muxiuesd.bedrockcore    框架层：UI 组件体系 / Codec / 文件 / 池 / Vec2 / 字体 / GL 兼容
       └ ttk.muxiuesd                 游戏层：注册表 / 系统 / 世界 / 实体 / 物品 / 渲染 / UI
```

**规范要求**：游戏强相关逻辑放 `ttk.muxiuesd`，可复用底层放 `game.muxiuesd.bedrockcore`，且**框架层不得反向依赖游戏层**。

**实际状态**：框架层 66 个文件中有 **9 个反向 import 了 `ttk.muxiuesd`**（23 条 import），并已成环：

- 环：`ttk/ui/components/FightUITextButton extends UITextButton`（游戏→框架）而 `bedrockcore/ui/components/UIButtonListItem extends FightUITextButton`（框架→游戏）。
- 症结：`Identifier`、`UIComponentsHolder`、`Pools`、`Util`、`GUICamera`、`Text`/`TextUtil`/`Fonts`、`Fight` 这些**被框架层当基础设施用、却定义在游戏层**的符号。
- 详见问题清单 **F-L1**。

## 三、五条主干机制

理解本项目只需抓住这五条，其余都是它们的组合。

### 3.1 能力认领制（渲染归属由接口决定）

```java
SystemManager.addSystem(name, system)
  └ if (system instanceof IRenderTask task) RenderProcessorManager.addRenderTask(task)
       └ 遍历所有 processor：processor.recognize(task)?
            └ if (task instanceof IWorldGroundEntityRender) { addRenderTask(task); return true; }
```

- 「系统」只要实现某个渲染能力接口，就被对应处理器**认领**，每帧回调其 `batchRender` / `shapeRender`。
- 实例：`EntitySystem implements IWorldGroundEntityRender, Tickable`（渲染调试碰撞箱）、`GroundEntityRenderSystem implements IWorldGroundEntityRender`（渲染地面实体）、`ChunkSystem implements IWorldChunkRender`、`GUISystem implements IGUIRender`。
- **硬约束**：必须先注册渲染处理器、再 `addSystem`，否则无人认领（只记 error 日志）。

### 3.2 两条正交的时间轴

| 轴 | 接口 | 频率 | 负责 |
|---|---|---|---|
| `update(float)` | `Updateable`（`GameSystem` 的钩子） | 每帧 | 位移、速度、碰撞箱、输入、渲染数据准备 |
| `tick(World, float)` | **独立接口 `Tickable`**（不是 GameSystem 的方法） | 20Hz | 状态机、活跃范围判定、线程池任务回收、刷怪、作物生长、方块实体逻辑 |

`Tickable` 只由 `TimeSystem` 驱动：`TicksPerSecond = 20`，累加 `tickSpan` 满 `1/20` 秒才触发，并把**实际间隔**传给 `tick`。

### 3.3 注册 = 身份，双索引查表

`Registries.DefaultRegistry` 内部是**双 LinkedHashMap**：

```java
LinkedHashMap<String, Identifier> idMap;    // id 字符串 → Identifier
LinkedHashMap<Identifier, T>      regedit;  // Identifier → 注册实例
```

`Identifier` 是**不可变值语义**（`final String id`、equals/hashCode 基于 id 字符串、无 setID），因此两套索引指向同一元素，既可按字符串查、也可按对象查。

**注册范式分两类**（架构约定）：

| 元素 | 注册什么 | 例子 |
|---|---|---|
| 全局唯一实例 | 直接注册实例 | `Item`、`Block`、`Wall`、`EntityType`、`DamageType`、`StatusEffect`、`Biome`、`EquipmentType`、`RenderLayer` |
| 需要独立状态 / 多样例 | 注册**工厂或 Provider**，或自带 `createSelf()` | `EntityProvider`、`BlockEntityProvider`；`BlockWithEntity` / `Botany` / `Wall` |

推论：**实体不能 `new`**，必须走 `EntityProvider.create(world)`（否则实体持有的 provider 为 null，`entity.getID()` 失效）。

### 3.4 三层数据归属

| 概念 | 归属 | 由谁读取 |
|---|---|---|
| 装备类型身份（id + 唯一实例） | `Registries.EQUIPMENT_TYPE` / `EquipmentTypes` | 物品模板、槽位门控 |
| 装备槽位（显示位置 + 背包下标 + 接受类型） | UI 面板里**手写**的 `EquipmentPlayerSlotUI` 实例 | 点击交互、行为层反查 |
| 装备容器（放什么、容量） | `LivingEntity.equipmentBackpack` | `DamageType` 减伤累加 |
| 物品行为 | `IItemStackBehaviour` + `Item.getBehaviour()` | `ItemStack.use` |
| 世界级常量（种子/时间/出生点/视野） | `WorldInfoTypes.*` 静态 map（`WorldInfo.INSTANCE` 只是壳） | 各系统 |

**要点**：物品**不携带位置信息**，位置由槽位决定；容量、类型数、槽位数三者**解耦**，配置不一致时显式失败（越界抛异常 / 未配置槽位返回 -1）。

### 3.5 线程边界

| 线程 | 允许做的事 |
|---|---|
| 后台线程池 | **纯数据**：区块噪声生成（`ChunkLoadTask`）、区块/实体 JSON 编解码（`ChunkUnloadTask`/`EntityLoadTask`/`EntityUnloadTask`） |
| 主线程（独占） | 一切世界状态变更：`addChunk`/`removeChunk`、`bePlaced`、方块/墙体/植物增删、实体系统装载、`initChunk`/`loadChunkBlocking` |

`getChunk` 找不到区块时**故意返回 null**（不同步生成），以免主线程卡顿与「幽灵区块」。

## 四、启动与生命周期

### 4.1 启动链

```
Lwjgl3Launcher.main
  └ new Lwjgl3Application(FightCore.getInstance(), config)
       └ FightCore.create()
            ├ coreInit()           Fonts / FI18N / EventTypes / RegistrantGroup
            │                      ShaderScheduler.init / RenderPipe.init / GameSystemManager.init
            ├ guiRenderProcessor = new GUIRenderProcessor(GUICamera, DEFAULT_SHADER, 10000) → 注册
            ├ new StartMenuScreen / WorldsMenuScreen / MainGameScreen
            ├ GameSystemManager.addSystem(InputHandleSystem / GUISystem / SpatialAudioSystem)
            ├ GameSystemManager.initAllSystems()
            └ setScreen(startMenuScreen)      // 只是写 nextScreen，下一帧才真正切换
```

### 4.2 每帧主循环

```
FightCore.render()
  1. exchangeScreen()                        延迟换屏（GameCore：hide 旧 → show 新）
  2. GameSystemManager.update(delta)         全局系统
  3. updateScreen(delta) → MainGameScreen.render → World.update → 各世界系统按注册序 update
  4. RenderPipe.handleGameRender()           更新相机 → swap() 冻结排序 → 逐处理器渲染
```

### 4.3 进入世界的初始化顺序（`MainGameScreen.show()`）

1. **注册表初始化**（顺序有强依赖）：
   `Pools → EquipmentTypes → EventTypes → Sounds → BlockEntities → Blocks → Walls → EntityTypes → Entities → StatusEffects → Items → WorldInfoTypes → ItemGroups → CraftingRecipes → BlockDropLootTables → EntityDeathLootTables`
   （`Items` 的静态字段会构造方块物品/装备物品，故方块/墙体/实体/音效/装备类型必须先完成类加载）
2. `new MainWorld(this)` → 构造内即 `readWorldInfo()`（先 `clear()` 四张静态 map 防串档）
3. `registerWorldRenderProcessors(world)` → 注册 4 个世界渲染处理器
4. `mainWorld.addAllSystems()` → 注册 18 个世界系统
5. `initAllSystems()` → 按插入序逐个 `initialize()`

### 4.4 世界系统注册顺序（= 每帧执行顺序，含语义依赖）

```
TimeSystem → EventSystem → PlayerSystem → ChunkSystem → PathfindingSystem → EntitySystem
→ UndergroundEntityRenderSystem → GroundEntityRenderSystem → ParticleSystem → CameraFollowSystem
→ GroundEntityCollisionSystem → BulletCollisionSystem → WorldInputHandleSystem → SoundSystem
→ MonsterGenerationSystem → UndergroundCreatureGenSystem → LightSystem → TestSystem
（SoundEffectSystem 已注释掉；MainWorld:25 注释说明"寻路系统需要在实体移动前更新流场"）
```

### 4.5 退出世界

`MainGameScreen.dispose()` → 注销 4 个世界渲染处理器 → `world.dispose()`（系统 dispose → `ChunkSystem` 同步保存全部活跃区块并关线程池 → `TimeSystem` 回写游戏时间 → `World` 写 `worldInfo.json`）→ **`guiRenderProcessor.setMainGameScreen(null)`**（GUI 处理器是全局常驻，不置空会继续对已 dispose 的世界做光照后处理）。

## 五、注册与序列化

### 5.1 注册表

`Registries` 持有 **28 张注册表**（`ALL_REGISTRY: Map<RegistryKey, Registry>`），元素类型包括：
`CODEC / ITEM / ITEM_GROUP / BLOCK / BLOCK_ENTITY / WALL / ENTITY_TYPE / ENTITY / DAMAGE_TYPE / PROPERTY_TYPE / STATUS_EFFECT / EQUIPMENT_TYPE / ITEM_STACK_BEHAVIOUR / COOKING_RECIPE / CRAFTING_RECIPE / AUDIOS / BLOCK_SOUNDS / RENDER_LAYER / 4×RENDERER / BLOCK_DROP_LOOT_TABLE / ENTITY_DEATH_LOOT_TABLE / BIOME / PARTICLE_EMITTER / POOL / WORLD_INFO_HASH_MAP / LANG_HOLDER`。

`Registry` 接口：`register / get(Identifier) / get(String) / getOrNull / contains / getMap`。
**注意**：`get` 未命中**抛异常**，`getOrNull` 才返回 null —— 存档解码等容错路径必须用 `getOrNull`（历史上有过一批评「null 判空是死代码」的问题都源于此）。

### 5.2 序列化框架（新式，无反射）

- `Codec<T>`：`encode(T) → RawObject`、`decode(RawObject) → DataResult<T>`。
- `RawObject`：单值包装 + `is/as` 类型检查。
- `DataResult`：三态 `Success / Error / **ErrorWithPartial**` —— 部分字段解码失败仍返回可用实例。
- `ObjectCodec`：由 `ParamField`（供工厂构造的参数）+ `FieldBinding`（setter 注入，带 `decodeOnRead` 开关）驱动，**全程零反射**；缺字段记 error 但**仍建实例**。
- `CodecBuilder0~3`：按构造参数个数逐级提升泛型，**最多 3 个构造参数**。
- 内置常量 Codec：`INT / STRING / BOOL / LONG / FLOAT / DOUBLE`，以及 `listOf / mapOf / arrayOf / xmap`。
- **旧式 Codec**（`app.interfaces.serialization.Codec`）已 `@Deprecated`，但旧 `JsonDataWriter/JsonDataReader` 仍在使用（世界菜单写档、`LangPack` 读语言文件）。

### 5.3 JSON 转换

`RawObjectJsonConverter` **全手写**：写入用 libGDX `JsonWriter` 递归；读取是自写的 `StringReader` 解析器。**与 gson 无关**（gson 仅声明依赖，零引用）。

**已知限制**：非法 JSON 抛 `RuntimeException`（无降级）；序列化时**值为 null 的字段不写入**（带键 null 的分支被注释掉）。

### 5.4 存档文件全景

根目录 `save/<世界名>/world/`：

| 文件 | 写入者 / 时机 | 原子写 | 读取容错 |
|---|---|---|---|
| `worldInfo.json` | `World.writeWorldInfo` ← `World.dispose`；建世界时另写一次 | 是 | **无 try-catch**（损坏直接抛） |
| `entities/player/player_data.json` | `PlayerSystem.savePlayerData` ← `PlayerSystem.dispose` | **否**（`writeString`） | **无 try-catch**；partial 也用 |
| `chunks/(x, y).json` | `ChunkUnloadTask`（异步提交） | 是 | 异常 → 退回内存区块或重新生成；逐格降级 |
| `entities/(x, y).json` | `EntityUnloadTask`（异步）/ `EntitySystem.dispose`（主线程） | 是 | 整体解析无 try；**单实体解码失败逐条跳过**，成功后才删文件 |

`WorldInfo` 的结构是 `{"fight:int|long|float|string": {key: value}}`；区块文件是 `{blocks, walls, botany, heights, canSpawn, biome}`。

## 六、系统层

### 6.1 基类契约

- `GameSystem`：`initialize()`（延迟初始化）/ `update` / `draw` / `renderShape` / `dispose`，持 `SystemManager`。**没有 tick**。
- `WorldSystem extends GameSystem`：唯一差异是持 `World`，构造时 `setManager(world.getSystemManager())` → **强制世界必须先有 manager**。
- `SystemManager`：`LinkedHashMap` 双表（`Class→name`、`name→GameSystem`）保序；`initAllSystems/update/dispose` 均按插入序；`addSystem` 对 `IRenderTask` 自动登记渲染任务。

### 6.2 Global（GameSystem）vs Per-World（WorldSystem）

| | 全局系统 | 世界系统 |
|---|---|---|
| 管理器 | `GameSystemManager`（单例） | `WorldSystemsManager`（每世界） |
| 成员 | `InputHandleSystem`、`GUISystem`、`SpatialAudioSystem` | 18 个（见 4.4） |
| 生命周期 | 注册于 `FightCore.create`，销毁于 `FightCore.dispose` | 起于 `MainGameScreen.show`，止于 `MainGameScreen.dispose` |

### 6.3 系统间通信

- 世界内：`getManager().getSystem(Class)` 或 `getWorld().getSystem(Class)`，通常在 `initialize`/构造里缓存成字段。
- 世界↔全局：经静态单例（`GUISystem.getInstance()`、`SpatialAudioSystem.getInstance()`）；反向用 `FightCore.getWorld()`。
- 解耦：`EventBus` 事件总线（见第九节）。
- **注意**：`getSystem(Class)` 只打 error 后返回 null，且按**精确 class** 匹配（查父类/接口必空）。

## 七、渲染管线

### 7.1 执行链

```
RenderPipe.handleGameRender()
  1. cameraControllers.forEach(camera.update())      相机自动更新
  2. RenderProcessorManager.swap()                   冻结排序快照（与注册共用同一把锁）
  3. handleRender(batch, shapeRenderer)
       逐处理器：batch.begin() + shapeRenderer.begin()      ← begin/end 归属在「管理器」
                 beginShader → handleBatchRender → handleShapeRender
                 catch 记日志 → finally: endShader / batch.end / shapeRenderer.end（各自独立 try）
```

**两级优先级是两个维度**：
- 处理器级 `renderOrder`（int，越小越先）= **相机与着色器的切换点**；
- 任务级 `IRenderTask.getRenderPriority` = **同一处理器内部**的任务顺序。

### 7.2 处理器清单

| 处理器 | renderOrder | 相机 | 着色器 | 认领接口 |
|---|---|---|---|---|
| `EntityUndergroundRenderProcessor` | 100 | PlayerCamera | DAYNIGHT | `IWorldUndergroundEntityRender` |
| `WorldChunkRenderProcessor` | 200 | PlayerCamera | DAYNIGHT | `IWorldChunkRender` |
| `EntityGroundRenderProcessor` | 300 | PlayerCamera | DAYNIGHT | `IWorldGroundEntityRender` |
| `ParticleRenderProcessor` | 400 | PlayerCamera | PARTICLE | `IWorldParticleRender` |
| `GUIRenderProcessor` | **10000** | GUICamera | DEFAULT | `IGUIRender` |

- **GUI 处理器是全局常驻**，并在画 GUI 前调用 `LightSystem.afterProcess()`（全屏光照后处理）。
- `WorldRenderProcessor` 持 `World` 字段，但**四个子类均未读取**（实际作用只是随处理器一起被丢弃）。
- 退出世界时前四个随 `MainGameScreen.dispose` 注销。

### 7.3 相机

| 相机 | 建法 | 基准视口 | 原点 |
|---|---|---|---|
| `PlayerCamera` | `setToOrtho(false,…)` | 16×16 | 世界中心，y 向上 |
| `GUICamera` | `setToOrtho(false,…)` | 512×512，position=(0,0) | 屏幕中心，y 向上 |

换算集中在 `CameraUtil`，对外入口是 `Util.getMouseWorldPosition()`（世界）与 `Util.getMouseUIPosition()`（GUI）。`CameraController.resize` 按横竖屏分别以 `h=base*h/w` 或 `w=base*w/h` 计算。

### 7.4 着色器

- `ShaderScheduler` 持 `id→ShaderProgram` 与 `activeShaders`，`begin` 做 `bind + batch.setShader`，`end` 做 `setShader(null)`；**无引用计数**，未成对 `end` 会抛异常（由管理器的吞异常 try 兜底）。
- 注册项：`DEFAULT`（GL32C 生成）、`DAYNIGHT`、`PARTICLE`、`PARTICLE_2`（后者无使用者）。
- **macOS 兼容层被绕过**：`GL32CMacIssueHandler` / `ShaderCompatibilityHelper` / `ShaderProgramFactory` 三处注释都承诺"涉及着色器编译全走这里"，但 `ShadersReg.register` 直接 `new ShaderProgram(vert, frag)`；着色器文件硬编码 `#version 330 core`，而兼容层用 `#version 150`。
- **uniform 实际使用面极窄**：全仓库只有 `u_projTrans` 两处 `setUniformMatrix`。

### 7.5 渲染器与上下文池

四类渲染器注册表（Block / BlockEntity / Entity / Item）结构相同（`extends DefaultRegistry`）。差异在容错：

- `EntityRendererRegistry.getRenderer` 用 `getOrNull`（渲染循环可判空跳过）；
- `BlockRendererRegistry.get` / `ItemRendererRegistry.get` 是"**打 error 后返回 null**"；
- `BlockEntityRendererRegistry` 不提供 `getOrNull`。

四类 `Context` 均池化（`FightPool` + `reset()`），约定 `obtain → 用完 freeContext`。

### 7.6 资源与音频

- `AssetsLoader` 单例：主 `FightAssetManager` + 每 mod 命名空间一个；`id.split(":")[0] == "fight"` 决定走哪个。`Class → (id → path)` 双层映射。
- `Resource`：`ofTextureRegion` 只注册映射，**首次 `get()` 才加载**；加载失败置空 loader。
- 音频全走 TuningFork（GDX 音频被禁）：`SoundSystem.playSpatialSound → SpatialAudioSystem → TFAudioEngine`；`AudioHolder` 只持 id + FileHandle（值语义），FileHandle 在 `Sounds.register` 时注册，播放时零查找。
- **3D 监听者从未摆位**：`TFAudioListener.setPos/setOrientation` 无调用者。

### 7.7 光照与粒子

- `LightSystem implements IWorldParticleRender`，被 Particle 处理器认领；预建 **256 个 HackLight** 池，每帧 `useLight()` 收集发光粒子光源。
- 真正的帧序确认者是 **GUI 处理器**：`afterProcess()` 算昼夜环境色 → `FightHackLightEngine.draw(PlayerCamera)` → 复位所有光源 scale。
- 光照 FBO 尺寸 `update(640, 480)` **硬编码且只在 initialize 调一次**，resize 不通告。
- 粒子：6 个共享单例发射器 + `ParticleSystem` 的三队列（active / delayAdd / delayRemove）驱动；动态贴图走 `setSummonRegion`（用完必须复位）。

## 八、世界 · 区块 · 方块 · 地形

### 8.1 Chunk 数据结构

- 四个 `[16][16]` 数组：`blocks`、`walls`、`botanys`、`heights`；另加标量 `biome`、`canSpawn`。
- **方块实体不在 Chunk 里**，而在 `ChunkSystem.blockEntities: Map<BlockWithEntity, BlockEntity>`。
- 坐标换算：世界→区块 `floor(w/16)`；区块→格内先 `round` 再对 16 取模（含负数补偿）；格内→世界 `cp*16 + c`。
- **`heights` 是"地形高度标量" 0~256**（不是世界 Y），并**逐格存档**。
- 高程常量：`SEA_LEVEL=150`（唯一海陆分界）、`BEACH_MAX=156`、`GRASS_TOP=200`、`STONE_TOP=235`、`SNOWLINE=236`。

### 8.2 加载 / 卸载（`ChunkSystem.update` 七段流水）

1. `delta == -1.2f` 是**特殊预加载哨兵**：同步 `initChunk` 玩家区块 + 加载其实体后 return；
2. 收已完成加载任务 → `addChunk` + `loadEntities`；
3. 收已完成卸载任务 → `removeChunk`；
4. `_loadChunks` 并入 `activeChunks`；
5. 提交卸载任务到线程池 → **立即清空 `_unloadChunks`**（防下一帧重复提交）；
6. 更新活跃区块 → 更新方块实体；
7. 0.5s 定时 + 玩家位移 ≥1.2 才重算加载/卸载范围。

触发范围：以玩家区块为中心 ±`PLAYER_VISUAL_RANGE`(16)，按距离阈值过滤；卸载半径按 `16×(16+16)/2 = 256` 世界单位。

### 8.3 方块体系

| 类别 | 实例规则 | `blockInstances` 键 |
|---|---|---|
| 普通方块 | **全世界共享一个实例** | 纯 id |
| `BlockWithEntity`、`Botany` | 每次出现一个独立实例 | `id@hashCode` |

- 因此 `removeBlockInstance` **只对独立实例调用**，普通方块永不移除。
- 墙体 `Wall extends Block`，也是"一个墙体一个实例"，靠 `createSelf(position)` 工厂创建。
- `Tickable` 的方块/方块实体在加入时同步注册进 `TimeSystem`。

### 8.4 方块实体生命周期

```
addBlockEntity → 注册 TimeSystem tick → setWorld → bePlaced
removeBlockEntity(block, dropItems):
    dropItems=true  → beDestroyed（掉落内容物）  ← 玩家破坏路径
    dropItems=false → 只移除，不掉落            ← 区块卸载路径（内容物随区块存档，防复制）
```
两个驱动者：每帧 `update` 由 `ChunkSystem`；20Hz `tick` 由 `TimeSystem`。

### 8.5 地形生成数据流

```
种子 → WorldMapNoise(Simplex)
  逐格 sampleHeight = map(noise(w/1000, h/1000), -1..1 → 0..256)
  区块海陆 = smoothedChunkHeight（本块 + 8 邻块【中心格高度】平均）< SEA_LEVEL
  河流 / 湖泊 / 湿地水塘 → 直接把该格高度压到海平面以下
  逐格 lookupLandBiome(该格温湿, 高度)：
        湿地强度 ≥0.5 且 ≥山地 → WETLAND；山地 (h-200)/40 ≥0.5 → MOUNTAIN
        否则 SNOWY/DESERT/FOREST 按 matchDegree 竞争，最高 <0.6 → PLAINS
  biome.decideBlock(height)：
        height < SEA_LEVEL → 水；否则在 bands 里【从高到低】找第一个 height ≥ startHeight
        未配置 bands 则用 DEFAULT_BANDS（150沙 / 157草 / 201石 / 236雪）
  墙体后置遍历：水上不生成，其余地格 1/16 概率
```
出生点是**存档属性**：存档无 `spawn_x` 才用 `SpawnPointFinder` 螺旋探查（用 `initChunk` 隔离生成，不写盘、不污染系统），结果写回世界信息。

## 九、实体 · 战斗 · 碰撞

### 9.1 继承树

```
Entity<T extends Entity<T>>              自引用泛型，setter 返回 T 实现链式
├── LivingEntity<T>                      生命 / 背包 + 装备背包 / 状态机 / 状态效果 / 挥手 / 击退
│   ├── Player                           无状态机（纯输入驱动）
│   ├── PathFindingEntity                逃跑、卡住脱困、流场与 A* 跟随
│   │   └── Enemy                       目标 / 视野 / 攻击范围 / 攻速 / 近战远程分发
│   │       ├── Zombie（3 个通用状态）
│   │       ├── Slime（3 个专用状态）
│   │       └── EntityTarget
│   └── CreatureEntity（随机游走 + 休息）
├── Bullet                               无生命无状态机，只受空气阻力，寿命到点自删
├── ItemEntity                           池化 + onAirTimer + 吸引态
└── EntityFishingHook                    自带 Timer 状态机
```

### 9.2 实体生命周期

```
EntityProvider.create(world)          工厂构造 + setProvider
  → EntitySystem.add → _delayAdd
  → _add：挂类型数组 / 渲染层级 / setEntitySystem / lazyInitialize（状态机 start 在此）
  → 每帧 updateEntities + 20Hz tick
  → 死亡 / 到期 / 子弹自删 → _delayRemove → _remove：反向清理 + freeSelf + dispose
```

**范围机制**：以到玩家中心距离判定，`≤ ENTITY_UPDATE_RANGE(32)` 入 `updatableEntity`，否则入 `incationEntity`（卸载候选池）；两数组互斥。区块卸载半径 256 ≫ 32，所以沉睡实体最终会随区块落盘。

### 9.3 状态机

- 契约：`LivingEntityState.start / handle / end`；`addState(id, state)` 注册，`setState(id)` 切换（执行 `end → start`）。
- 实现只有**敌人/生物两族**；**玩家没有任何状态**。
- 寻路协作：状态内调 `walkToTarget` / `fleeFrom` / `keepDistance` / `getFlowDirection`；`PathfindingSystem` 维护 64×64 流场（全场最大半径膨胀、0.4s / 目标移动 1 格 / 墙体变更触发重建），独立目标走 A* 且限 4 次/帧。
- **击退暂停状态机**：先 `updateKnockback`，再判 `isKnockback()` 决定是否 `handle`。

### 9.4 伤害与状态效果

- `DamageType<S, T extends LivingEntity<?>>`：`S` 任意来源、`T` 固定活物；`apply` 抽象，`computeKnockback` 默认 0，`computeDamageReduction` **遍历目标装备背包**累加 `DAMAGE_REDUCTION`。
- 四种实现：`BULLET`（取 `Bullet.damage`）、`SWORD`（读手持 `WEAPON_DAMAGE`/`WEAPON_KNOCKBACK`，缺省回退 2）、`MELEE`（读 `Enemy.meleeDamage`）、`STATUS_EFFECT`（不减伤）。
- `LivingEntity.applyDamage`：`apply → setAttacked(true)(0.03s) → computeKnockback（来源必须是 Entity 才击退）`。
- `StatusEffect` 由 `LivingEntity.effects` + 两个池化 Timer（20Hz / 1s）驱动，**无到期回调**；目前只有毒与治疗。

### 9.5 碰撞

- `Hitbox`：`isApproach` 用"半径和 ≥ 中心距"做粗筛；`RectHitbox` 用 `float[6]` 存中心 + 起止偏移。
- `HitboxHolder`：命名碰撞箱 + `CollidedAction`，缺 id 返回 `VOID_HITBOX` / `VOID_ACTION`。
- 地面/墙体：按 `|v|·delta/MAX_STEP` **分步（CCD 防隧穿）**，每步 X/Y 同移后 `fixCollisions` 取**最小侵入轴**分离，撞轴清零速度；另有实体间软推开力。
- 子弹：只遍历玩家/敌人子弹数组；`pathBounds` 用实际 delta；步长 ≤ 子弹半宽；目标由 owner 类型决定。

### 9.6 事件系统

- `EventBus` 是**全局静态表**（`eventType → EventHandler`），`EventTypes` 在静态字段里注册 8 种类型，每种自带 `callEvents` 派发逻辑（泛型 `EventHandler<T extends Event, P extends EventPoster>` 提供签名级类型校验）。
- 8 种：`BulletShoot / EntityHurt / EntityDeath / PlayerDeath / WorldTick / BlockReplace / WorldKeyInput / WorldButtonInput`。
- **订阅是每世界的**：`EventSystem.initialize` 订阅（实际只订 6 种），`dispose` 统一 `unsubscribe` 防重进世界累积重复订阅。

## 十、物品 · 容器 · UI

### 10.1 模板 / 堆叠分离

| | `Item`（模板） | `ItemStack`（堆叠） |
|---|---|---|
| 实例 | 全局唯一（注册进 `Registries.ITEM`） | 每次获得/掉落/拾取新建 |
| 持有 | 无 | 背包槽 / 手持 / 掉落物实体 / 鼠标槽 |
| 属性 | 模板原始属性（**不直接操作**） | 模板属性的**副本**，可随意改 |
| 行为 | `getBehaviour()` 返回注册单例 | `behaviour` 字段 |
| 贴图 | 不持有 | 由 `ItemRendererRegistry` 的渲染器持有 |

### 10.2 属性与行为

- **属性三层来源**：`Item.Property()` 默认（maxCount 64 / on_using false / 音效 ITEM_CLICK）→ 子类 `createDefaultProperty()`（武器：1 / 伤害 1 / 击退 2 / 耐久 100 / 间隔 1）→ Builder 覆写。
- **两套浅拷贝语义**：`JsonPropertiesMap.copy()` 只对实现 `ShallowCopyable` 的值深拷（现仅 `CatsHolder`），其余**共享引用**（基本类型不可变 / `AudioHolder` 无状态 / `BlockSounds` 单例 / `Entity` 引用本就应共享）。
- **堆叠判定**：`item 引用相同 && 属性 map 全等` ⇒ **耐久或 `ITEM_ON_USING` 一变即不可合并**（设计语义）。
- **行为 5 种**：`COMMON / CONSUMPTION / SWORD / RANGED_WEAPON / EQUIPMENT`。
- **耐久 · CD · `ITEM_ON_USING` 联动**：`useTimer` 由 `WEAPON_USE_SAPN` 在 `setItem` 创建且**初值已就绪**；`isUsing()` **只读比较** `curSpan < maxSpan`（**绝不能调 `isReady()`**，它会归零 curSpan）；CD 完成由 `ItemStack.update` 复位；`setHandIndex` 用 `isUsing()` 静默拦截切换。

### 10.3 容器

- `Inventory`：实现类只需 6 个存储方法，其余（`addItem` / `dropItem` / `pickUpItem` / `clear` / `isFull` / `exceed` / `update`）由 default 提供。
- `Backpack`：`map + size`；越界抛异常；序列化 `{"size", "items": {下标: stack}}`，只写非 VOID。
- **空态统一**：`ItemStack.VOID` 单例 + `isVoid()` 用 `==`；**null 只存在于 `Backpack` 内部，不外泄**（`get null→VOID`、`set VOID→null`、`update` 清 null 键）。
- **`getSize()` = 槽位总数；`getCapacity()` = 非空槽数**。
- 装备背包 `LivingEntity.equipmentBackpack`，容量 `DEFAULT_EQUIPMENT_BACKPACK_SIZE = 4`（**独立于注册类型数量**）；写方是装备行为与装备槽位，读方是 `DamageType`。

### 10.4 UI 三层与槽位绑定

| 层 | 职责 |
|---|---|
| `Screen`（libGDX） | **薄壳**：只持有 `UIScreen`，`show` 里 `GUISystem.setCurScreen`，`render` 只清屏 + 读退出键 |
| `UIScreen` | 组件集合、每帧命中检测、焦点、拖拽捕获、延迟增删、`InputProcessor` 转发 |
| `UIPanel` / `UIComponent` | 面板 = 容器 + 可绘制者（自引用）；组件 = 叶子；子坐标相对父面板 |

- **槽位读写位置**由 `PlayerSlotUI.getInventory() + getIndex()` 决定 —— 「换容器」= 覆写 `getInventory()`（装备槽就是这样接上装备背包的）。
- **槽位绑定权威在写 UI 处**：`PlayerInventoryUIPanel` 定 0-8 快捷栏、9-35 背包、装备 `type→下标`。
- **点击交互四分支**（左键）：槽有物+鼠标空（Shift 半数 / 否则整叠搬）；鼠标有物（`checkItemType` 后 equals 则 merge、否则交换）；槽空+鼠标有物（放入并失活）；末尾无条件 `backpack.clear()` 清 0 数量。
- **方案 A / 方案 B 的成因**：槽位是"拿起→拖动→放下"**连续手势**，必须按下即取物（方案 A）；按钮**无拖拽语义**，才能"移出取消"（方案 B）。
- `MouseSlotUI` 是**无容器的单例**（覆写数据方法），活跃判定 `curScreen != null` 且需同屏。

### 10.5 输入门控

- **两条不共享门控的轨道**：
  - 键盘：`UIScreen implements InputProcessor`，复用 `KeyBindings`；
  - 鼠标：**`UIScreen.update` 每帧轮询 `Gdx.input` 并硬编码 `Input.Buttons.LEFT/RIGHT`**，不走 KeyBindings。
- `GUISystem.mouseOverUI()` = `curScreen != null && screen.isMouseOver()`。
- `PlayerSystem.handleInput`：**鼠标块**需 `isHUD && !mouseOverUI()`；**键盘块**（含移动）只需 `isHUD`；非 HUD 强制 `setVelocity(0,0)`。
- `WorldInputHandleSystem`：全局键（ESC/C/H/F/P/E）不受 UI 影响；世界交互需 `curScreen == HUD && !mouseOverUI()`；滚轮需 `curScreen == HUD`。
- **禁用矩阵**：背包打开 → 世界交互/滚轮/移动全禁，但全局键仍生效；HUD 且鼠标在 UI 上 → 鼠标类与世界交互禁用，键盘移动照常。

### 10.6 文本与多语言

- `Text`：`textKey + StringBuilder + args[10]`；`{i}` 占位符；`&&x` 颜色标记（13 色）。
- `FI18N.ZH_CN` 类初始化即加载 `lang/zh_cn.json`；`LangPack` 为平铺 HashMap，**缺 key 直接返回 key 本身**。
- 字体仅 `Fonts.MC`，`FontHolder` 按字号缓存**共享** `BitmapFont`（`FONT_SIZE=16`、`FONT_SCALE=0.5`）；组件在 draw 前置 0.5、尾部恢复 1（共享示例的副作用）。

## 十二、硬约定清单（改动时必须遵守）

1. **`WorldSystem` 必须晚于 `WorldSystemsManager` 创建**（构造时即取 manager）。
2. **先注册渲染处理器，再 `addSystem`**，否则渲染任务无人认领。
3. **系统注册顺序 = 每帧执行顺序**（`LinkedHashMap`），有时间依赖的系统必须按序添加。
4. **实体必须经 `EntityProvider.create`**，不能自行 `new`。
5. **注册表的 `get` 抛异常、`getOrNull` 返回 null**；容错路径用后者。
6. **`Identifier` 注册后不可变**；覆盖注册会替换而非残留。
7. **容器只暴露存储方法**，行为由 `Inventory` 的 default 提供。
8. **空态统一 `VOID`**，`null` 不得外泄（`Backpack` 内部转换）。
9. **模板不可变、堆叠持副本**；配方/物品组的输出是全局共享实例，进容器前必须 `copy()`。
10. **注册依赖静态类加载顺序**（多数 `init()` 是空方法，仅用于触发类加载）。
11. **坐标/下标/接受类型的唯一权威是写 UI 的代码**；行为侧只反查。
12. **渲染 `Context` 必须 `obtain → freeContext` 成对**。
13. **`isUsing()` 不可用 `isReady()` 实现**（归零副作用）。
14. **退出世界必须 `guiRenderProcessor.setMainGameScreen(null)`**。
15. **未知 id / 未知属性类型解码要跳过**，保证旧存档兼容。

## 十四、设计语义（**不是缺陷，勿改**）

1. 浅拷贝方案 A：仅实现 `ShallowCopyable` 的值深拷，其余共享引用。
2. 耐久或 `ITEM_ON_USING` 不同的同类物品**不可堆叠**。
3. **耐久耗尽后物品不销毁**，只播破损音效 + 拒绝使用。
4. **`PlayerSystem.debugMode` 默认 `true`，且背包为空时会发放 22 件测试物品**（`PlayerSystem.setPlayer → PlayerDebugger.items`）——这是**开发期刻意设计**（快速取得测试素材），随时可置 `false` 关闭；**不得当作缺陷**（见问题清单 `I-E4`）。
5. `useTimer` 初值即"已就绪"；`isUsing()` 只读比较，不得调 `isReady()`。
6. 装备背包容量（4）**独立于**注册的装备类型数量。
7. 装备槽位的显示位置与背包下标**由写 UI 的人手写决定**，注册表只给类型身份。
8. 死亡 / 破坏 / 钓鱼掉落的物品**可立即拾取**；2 秒保护只针对玩家主动丢弃。
9. 未知 id / 未知属性类型解码**跳过**，保证旧存档兼容。
10. `getChunk` 找不到区块**返回 null**，不同步生成。
11. 后台线程**只做纯数据**，绝不触碰世界状态。
