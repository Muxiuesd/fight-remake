## 0. 一页结论

**逻辑主干是清晰的，而且是自洽的。** 五个机制把 533 个文件串成了一个可解释的整体：

1. **能力认领制**——对象只实现自己需要的接口（`Updateable` 每帧、`Tickable` 20Hz、`Disposable`、`Codecable`、`ICatData`），系统按接口认领，不存在"上帝基类"。
2. **系统串行流水线**——一个世界 20 个系统，`SystemManager` 用 `LinkedHashMap` 保证"初始化顺序 = 每帧更新顺序 = dispose 顺序"，所有跨系统协作都在这一条主线上。
3. **注册即身份**——注册表把 `Identifier`（`命名空间:路径`）映射到对象；单例注册实例、多实例注册工厂，存档只存 id。
4. **两条正交时间轴**——`update(delta)` 每帧变步长（物理/输入/渲染），`Tickable.tick` 固定 ~20Hz（生长/计时/生成）。二者不混用是性能与确定性的分界。
5. **异步区块装卸 + 原子写盘**——`ChunkLoadTask`/`ChunkUnloadTask` 在线程池里跑，主线程只收割 `Future`；`writeFileAtomic` 保证不写半个文件。

**但有三个结构性紧张点，几乎所有的坑都从这三处冒出来：**

|---|---|---|---|

## 1. 全局架构

### 1.1 分层与依赖方向

```
lwjgl3/  (桌面启动器)
  └─ Lwjgl3Launcher → FightCore (extends GameCore, 属于框架层)
core/    game.muxiuesd.bedrockcore   ← 可复用框架层（无游戏内容）
         ttk.muxiuesd                ← 游戏层（方块/物品/实体/世界/UI）
```

**硬约定**：`game.muxiuesd.bedrockcore` 不得依赖 `ttk.muxiuesd`。
**现状**：仍有 9 个框架层文件反向 import 游戏层（清单 `F-L1`），最典型的是 `bedrockcore/app/ui/abs/UIScreen` 用到 `ttk.muxiuesd.ui` 的具体组件、`UIScreen` 与 `FightUIScreen` 形成继承环。这一层"分不干净"直接导致框架层无法独立复用（也是第十一章 `F-L1` 一直挂着的原因）。

**判断**：分层理念正确，但边界只在包名上成立，在类型依赖上没有成立。若未来要做 mod/多前端，这一条必须先解决；若只做单游戏，可以视为"可接受的技术债"，但要停止在框架层继续加游戏类型。

### 1.2 启动链

| 阶段 | 位置 | 动作 |
|---|---|---|
| ① 桌面启动 | `lwjgl3/.../Lwjgl3Launcher` | 配置窗口、`Lwjgl3Application(new FightCore(), config)` |
| ② 框架初始化 | `FightCore.create()` → `coreInit()` | `Fonts.init` → `FI18N.init` → `EventTypes.init` → `RegistrantGroup.init` → `ShaderScheduler.init` → `RenderPipe.init` → `GameSystemManager.init` |
| ③ GUI 处理器 | `FightCore.create()` | 先注册 `RenderProcessorsReg.GUI`（order 10000），保证它**第一个注册、最后绘制** |
| ④ 建屏 | `FightCore.create()` | `StartMenuScreen` / `WorldsMenuUIScreen` / `MainGameScreen` 三个 screen 常驻 |
| ⑤ 全局系统 | `FightCore.create()` | `InputHandleSystem`、`GUISystem`、`SpatialAudioSystem` 加到 `GameSystemManager`，`initAllSystems()` |
| ⑥ 首屏 | `FightCore.create()` | `setScreen(startMenuScreen)` |

**注意点**：`GameSystemManager`（全局，3 个系统）与 `WorldSystemsManager`（每世界，20 个系统）是**两套独立管理器**，互不知情。全局系统在 `MainGameScreen` 之外也在跑——这正是"退出世界后输入处理器仍分发"（`P-A6`）的结构原因。

### 1.3 每帧主循环

`FightCore.render()` 只有五步，顺序不可换：

```
exchangeScreen()                      // 换屏
deltaTime = min(Gdx.graphics.getDeltaTime(), 上限)
Perf.begin("frame")                   // 性能记录
GameSystemManager.update(dt)          // ← game_system_update
updateScreen(dt)                      // ← game_screen_update → screen.render(dt) → world.update(dt)
RenderPipe.handleGameRender()         // ← game_render：相机更新 → 快照处理器 → 按 order 升序绘制
Perf.end()
```

**关键事实**：
- `MainGameScreen.render(delta)` 只做 `ScreenUtils.clear(BLACK)` + `world.update(delta)`，**实际绘制全部在渲染处理器里**。屏幕不持有绘制逻辑，这是好设计。
- 渲染处理器**没有 `process(delta)`**，顺序纯靠 `getRenderOrder()` 升序：`ENTITY_UNDERGROUND(100) → WORLD_CHUNK(200) → ENTITY_GROUND(300) → PARTICLE(400) → GUI(10000)`。
- 每个处理器自己 `begin()/end()`（`RenderProcessorManager:129-130`），GUI 最后画，所以 UI 永远盖在世界之上。
- `Perf` 只在按 `P` 时打印；`begin()/end()` 每次 `render` 成对调用，`end()` 把上一帧的 `Data` 回池，**没有泄漏**（复核时曾误判，见 §3.1 B1）。

### 1.4 世界初始化顺序

`MainGameScreen.show()`（:39-57）是**唯一**的注册入口，顺序有依赖，不能随意调整：

```
Pools → EquipmentTypes → EventTypes → Sounds → BlockEntities → Blocks(:46) → Walls
→ EntityTypes → Entities → StatusEffects → Items(:51) → WorldInfoTypes → ItemGroups
→ CraftingRecipes → BlockDropLootTables → EntityDeathLootTables → AttachmentPlacements(:57)
→ new MainWorld(this) → registerWorldRenderProcessors → addAllSystems → setWorld → initAllSystems
```

依赖关系（为什么是这个顺序）：

- `Blocks` 要在 `Sounds` 之后：方块属性里引用 `Sounds.GRASS` 等。
- `Items` 要在 `Blocks` 之后：`Items.POTATO = register("potato", Blocks.POTATO)` 需要方块原型，并回写 `crop.setDroppedItem(cropItem)`。
- `AttachmentPlacements` 要最后：规则里引用 `Blocks.POTATO` / `Blocks.FARMLAND_DRY`，方块字段必须已赋值。为防止有人把它提前，`Blocks` 末尾加了 `static final boolean READY = true;`（`Blocks.java:313`）作为"字段已全部初始化"的标记，`AttachmentPlacements.init()` 检查它。

**这是一个正确且优雅的做法**：用类的静态初始化顺序表达"数据依赖"，并加一个可检查的哨兵。缺点是哨兵本身是包级私有布尔值，只能防"调用顺序错"，防不了"静态块里提前引用"。

**世界系统注册顺序**（`MainWorld.addAllSystems`，20 个）：

```
TimeSystem → EventSystem → PlayerSystem → ChunkSystem → ChunkRenderSystem
→ PathfindingSystem → EntitySystem → UndergroundEntityRenderSystem → GroundEntityRenderSystem
→ ParticleSystem → CameraFollowSystem → GroundEntityCollisionSystem(注册名 EntityCollisionSystem)
→ BulletCollisionSystem → WorldInputHandleSystem → SoundSystem → MonsterGenerationSystem
→ UndergroundCreatureGenSystem → LightSystem → TestSystem
```

这条顺序的语义是：**时间 → 玩家意图 → 世界数据 → 空间查询 → 实体推进 → 渲染提交 → 输入/音频/生成**。`WorldInputHandleSystem` 排在实体之后，意味着玩家点击使用的是"本帧已经推进完"的世界状态，不会出现"点到了上一帧的位置"。

### 1.5 两条正交时间轴

| | `Updateable.update(delta)` | `Tickable.tick(world, delta)` |
|---|---|---|
| 频率 | 每帧 | 约 20Hz（`TimeSystem.TickMaxSpan = 1/20`） |
| 驱动 | `World.update` → `SystemManager.update` | `TimeSystem.update` 内累计 `tickSpan` |
| 步长 | 真实 delta（可变） | 传入的是**累积 span**（含上一帧余量） |
| 适用 | 物理、输入、渲染、碰撞 | 作物生长、怪物生成、状态效果计时 |
| 风险 | 帧率抖动影响手感 → 用固定半衰期加速模型规避 | 不等间隔 → 生长是概率性的，不能用来做精确计时 |

**这里的实现细节值得记录**：`TimeSystem.update` 是 `if (tickSpan >= TickMaxSpan) { tick(...); tickSpan = 0; } else tickSpan += delta;`——不是"每 50ms 一次"，而是"至少 50ms 才 tick 一次，然后把余量丢掉"。好处是不会追帧（低帧率时不会连发 tick 卡住），代价是 tick 频率略低于 20Hz 且抖动。对"作物生长概率 0.1%"这种用途完全够用，但**不要**把需要精确时序的逻辑挂到 `tick` 上。

### 1.6 注册=身份 / 三层数据归属 / 线程边界

**注册=身份**：`Identifier` 是值对象（不可变、有 `equals/hashCode`、正则校验），注册表用 `Identifier` 做键。单实例类型（`Block` 的普通方块、`Item`、`Biome`）注册**对象本身**；多实例类型（`BlockWithEntity`、每格独享的 `Attachment`）注册**工厂**（`EntityProvider` / `createSelf()`）。

**三层数据归属**（这条是理解整个世界的钥匙）：

| 层 | 归属 | 生命周期 | 例子 |
|---|---|---|---|
| 静态原型 | 注册表（`Registries.BLOCK` 等） | 进程级，永不销毁 | `Blocks.STONE`、`Items.POTATO`、`Wheat` 原型 |
| 每格实例 | `Chunk.blocks/walls/attachments` 数组 | 随区块加载/卸载/存档 | 种下的土豆（`growLevel`）、墙体实例 |
| 系统索引 | `ChunkSystem.blockInstances` / `blockEntities` / `TimeSystem.tickUpdates` | 随"进入/离开 activeChunks" | 可 tick 的方块、方块实体 |

**最危险的正是第三层**：它必须与第二层严格同步。`addChunk` 补登记、`removeChunk` 摘除，是这套设计的两个收口点；历史上"读档出来的植物不生长/挖下方方块崩溃"（`P-B10`）就是这两个收口点漏了附着物。

**线程边界**：
- 主线程：所有 `Chunk` 数组读写、`blockInstances`/`blockEntities`、`TimeSystem`、实体系统、渲染。
- 池线程（48）：`ChunkLoadTask`（读档/生成）、`ChunkUnloadTask`（写档）。
- 约定：池线程只允许**构造一个还没被世界引用的 `Chunk`**；一旦它被 `addChunk` 收编，就只能主线程动。§0 的 S1 就是这条约定被打破。

### 1.8 第二轮重读：六个机制是怎么咬合的，边界又松在哪

把 `§1.6` 的六个机制按"谁决定谁"重排一遍，整个项目其实只有一条主轴：

```
注册=身份  →  系统串行（update 顺序 = 可见性顺序）
                   ├─ 两条时间轴：每帧 update 管"表现"，20Hz tick 管"世界时间"
                   ├─ 异步区块：在途区块用"不可见/返回 null"表达，绝不阻塞主线程
                   ├─ 池化：让上面三条在每帧都做到零分配
                   └─ 事件：方块变了 → 声音/寻路/成就，系统之间不直接互相调用
```

**关键认识**：区块数组是"世界状态的唯一真相"，所有方块级副作用必须从 `ChunkSystem` 出。`Chunk.setBlock` 无条件转发 `addBlock`（`D1`）就是这条纪律的**强制点**——它保证了"写进区块数组"与"登记进系统"永远同时发生，代价是生成线程也被一起拉进了这条纪律（S1）。

**三处"边界纪律"**，也就是三处松动：

| 边界 | 正确纪律 | 现状 | 对应 |
|---|---|---|---|
| **线程**：谁可以写区块 | 只有主线程；生成线程先造"裸 `Chunk`"，挂载时再登记 | `MainWorldChunkGenerator` 拿到的是带 `chunkSystem` 的 `Chunk`，生成期就调 `addBlock` | S1 / `N2` |
| **降级**：读档失败怎么办 | 保留已解出的数据 + 报错 + 备份原文件，绝不用新地形覆盖 | 降级保留（`D3` 刻意），但静默且卸载时写回覆盖 | S2 / `N1` |
| **容错**：登记缺失、系统找不到 | 统一策略，缺登记就抛或显式命名 `…OrNull` | 同一类缺失，`getSystem(String)` 抛、`getSystem(Class)` 返 null；`removeBlockInstance` 对方块抛、对附着物只记日志 | S3 / `B7` / `B15` |

**刻意设计不是缺陷，但都有代价**：`D2`/`D9` 用"在途不可见"换确定性（代价：≤1 帧的读取空窗，且只影响排在 `ChunkSystem` 前的系统）；`D8` 用"五处查重"换无重复实例（代价：`chunkExist` 复杂度高，新增挂载路径必须一并接入）；`D12` 用"返回 null"换可选系统（代价：调用方被迫写判空，且与另一种策略并存）。

一句话：这套设计是**以系统串行换取确定性**；代价是任何跨线程、跨生命周期的行为都必须显式声明。现有三处松动，本质都是"某条路径隐式地跨了边界"。

- `ChunkRenderSystem:74` 硬编码 `PlayerCamera.INSTANCE`，`collectVisibleChunks` 在 `:105` 与 `:212` 被算两次。
- `RenderProcessorManager:129-130` 的两个 `begin()` 在 `try` 之外，begin 抛异常时 `finally` 不会执行 → 管线可能永久停在"未 begin"状态。
- `CameraController:20` 用整数除法算视口高 → 1280×720 比例本就是错的（`P-C12`），窗口高>宽时视口高为 0（黑屏）。

## 3. 模块评审

> 每节格式：职责 → 优点 → 不足（编号 + 证据 + 后果）。不足条目尽量落到文件:行。

### 3.1 框架层 `game.muxiuesd.bedrockcore`

**职责**：`GameCore`/`GameSystem`/`SystemManager` 基类、`Codec` 序列化、`UIScreen`/`UIPanel` 基类、资源与文件、日志、性能记录。

**优点**
- `Codec` 的组合式设计（field/paramField/factory/optional）让存档结构可读、可增量演进；`DataResult` 区分 `result` 与 `error`，允许"部分解码成功"。
- `RawObjectJsonConverter` 是唯一 JSON 入口，其他层不直接碰 gson（gson 在游戏层零引用，这点做得干净）。
- `UIScreen` 的延迟增删队列是可复用 UI 框架里少见的正确实现。

**不足**
- **B1 `PerfRecorder.begin()` 的 `if (curDataStack.empty()) return;` 是冗余守卫**（**修正：不是泄漏**）：`begin()`(:38-44) 空栈时提前返回，但此时 `clear()` 本就无事可做；非空时正常清空，`end()`(:49-59) 会把上一帧 `Data` 回池。**本次审计一度误判为"内存无界增长"，逐行复核后否定**——保留此条只为提醒：这类"看起来在防什么"的守卫容易把人带偏，按 `docs/开发规范约定.md` 一.6 可删。
- **B2 `Codec.BOOL` 把 `0` 解成 `true`**【清单 F-M5】：`:100-105` `if (value == 0) return success(true)`，与注释"非法值一律 false"相反。目前只有手写 JSON 才会触发，属潜伏。
- **B3 `Codec.STRING` 把 null 解成 `"Null_String"`**【清单 F-M6】：魔法串替换 null，一旦有 null 字段进入 codec 就被静默转成字符串。
- **B4 框架层反向依赖游戏层**【清单 F-L1】：9 个文件、UI 继承环。分层只在包名上成立。

### 3.2 注册与数据（`registrant/`、`id/`、`property/`、`data/`）

**职责**：`Identifier` 值语义、注册表（`Registries`）、属性表（`Property`/`PropertyType`/`JsonPropertiesMap`）、`CatData` 序列化。

**优点**
- `Registries.get()` **永不返回 null**（未注册直接抛带 id 的异常），`getOrNull()` 是唯一可空入口且注释写明"用于存档解码"——**契约清晰**，这是全项目最值得保持的设计之一。
- `Identifier` 不可变 + 正则校验 + 正确的 `equals/hashCode`（`H13` 修好之后），可以安全做 `HashMap` 键。
- `JsonPropertiesMap` 用类型化 map 而不是 `Map<String,Object>`，读的时候不需要强转。

**不足**
- `CodecJsonPropertiesMap:52-57` 用 `get()` 再判空：判空不可达，而"旧存档未知属性跳过"的意图永远不会发生 → 应改 `getOrNull`（正确范式在同目录 `JsonPropertiesMap:132-137`）。
- `SystemManager.getSystem(Class)` 是**精确 class 匹配**（`F-O2`）：传父类/接口必返回 null，且只 `Log.error` 不抛，与 `getSystem(String)` 语义相反。
- `Identifier.hashCode()` 的 `id == null ? 0` 分支不可达（`final` 字段 + 构造校验），属自我兜底。

### 3.3 系统管理器与时间（`system/abs/`、`TimeSystem`）

**职责**：系统注册/初始化/更新/dispose；游戏时间与 ~20Hz tick。

**优点**
- 一个 `LinkedHashMap` 同时决定"初始化顺序、更新顺序、dispose 顺序"，简单且无歧义。
- `TimeSystem` 把游戏时间存进 `WorldInfoTypes`，`dispose` 时写回，省掉一条独立的存档路径；`isDay/isDusk/isNight` 分区清楚。

**不足**
- **B5 `addSystem` 覆盖同名系统时摘错对象**【清单 M7，复核仍成立】：`SystemManager.java:38` `if (system instanceof IRenderTask task) removeSystemRenderTask(task);` 摘的是**新**系统（应为 `oldSystem`），`:46` 又对同一个 `system` 判一次。
- **B6 `dispose()` 不清理渲染任务**：只管 `Disposable::dispose`，退出世界后旧处理器若还挂在 `RenderProcessorManager` 里就会指向已销毁世界（与 `P-A6` 输入处理器泄漏同构）。
- **B7 `getSystem(Class)` 返回 null**（同 §3.2，**第二轮改判"设计不一致"**）：这是"可选系统"语义（`placeWall:535-536` 等 `if (pathfindingSystem != null)` 依赖它），但与 `getSystem(String)` 抛异常并存。建议改名 `getSystemOrNull(Class)`，把语义写进名字，而不是统一成抛。
- **B8 0 点整不算白天**【**第二轮改判"边界取舍"**】：`isDay() = gameTime > 0 && <= 9.6`，`00:00` 那一瞬间三个时段全 false。`gameTime ∈ [0,24)` 且每帧步进很小，影响 1 帧；改则三处一起改成 `>= 0`。

### 3.4 世界（`world/World`、`MainWorld`）

**职责**：持有系统管理器与世界信息，驱动每帧更新，负责世界级存档读写。

**优点**：`readWorldInfo()` 先清空 `WorldInfoTypes` 的四个 map 再解码，防止"上一个世界的信息串到下一个世界"——这是个容易被忽略但很关键的正确性细节。

**不足**
- **B9 `setWorldName` 条件写反**【清单 H7】：`:67-73` `if (worldName == null || !worldName.isBlank())` 时报错，即"合法名字被拒、空白名才能设置"。目前零调用方（世界名走 `WorldSaveButtonUI` 直接设 `Fight.WORLD_NAME`），**不可触发**，但一旦有人启用就是必崩。
- `writeWorldInfo` 失败只 `Log.error`（存档丢失无感知，与 S2 同源）。
- `getSystemManager()` 为 null 时 `Log.error` + `throw new RuntimeException()`（无 message），日志与异常二选一即可。

### 3.5 区块系统（`ChunkSystem`、`Chunk`、`ChunkLoadTask`、`ChunkUnloadTask`、生成器）

**职责**：区块装卸、方块/墙体/附着物三层读写、实例登记、存档写盘、可见区块查询。

**优点**
- 装卸全异步 + 原子写盘 + 中断检查（`ChunkLoadTask:26/33/59` + `chunkExist:827`），在"不加锁"的前提下做到了"同文件不并发读写"。
- 逐格解码容错（`CodecChunk:93-144`）：一个坏格降级，不废弃整块区块；高度做范围夹取。
- `removeChunk` 用 `dropItems=false` 并写清理由，避免"卸载掉包 → 重载复制物品"。
- 方块/墙体/附着物三层数据结构相同、操作对称，读代码时不需要记三套规则。

**不足**
- **B10 读档失败静默降级并被写回（数据丢失）**【S2，`【新】`】：`ChunkLoadTask:48-57` 解码错误只 `System.out`、异常被 catch 且 `printStackTrace` 被注释，然后 `optional.orElse(genNewChunk())`；卸载时 `ChunkUnloadTask` 用新地形整块覆盖同名文件 → **玩家建筑永久丢失且无日志**。这是本项目**唯一会丢数据**的缺陷，应最高优先修：至少把 `genNewChunk()` 换成"抛出 + 标记该区块只读/备份原文件"。
- **B11 生成线程直接写全局实例表**【S1，`【新】`】：`MainWorldChunkGenerator:46` `new Chunk(cs)` → `:70` `chunk.setBlock(...)` → `Chunk.setBlock:126-128` → `ChunkSystem.addBlock`（每个区块 256 次）。池线程因此执行 `blockInstances.put`、`TimeSystem.add`（`HashMap`/`Array` 非线程安全），48 线程与主线程数据竞争；中断时还会留下半登记实例。**建议**：生成时用 `new Chunk()`（无 system），由主线程 `addChunk` 统一登记。
- **B12 `getChunk` 只认 `activeChunks`**【`【新】`，**第二轮撤销：这是 D2 的刻意设计**】：`getChunk:950-953` 注释写明"在途返回 null"是为了①不卡主线程、②不产生幽灵区块；`addChunk:167` 与并入 `activeChunks:189-192` 在**同一次 `update`** 内完成，所以只有排在 `ChunkSystem` 之前的 `PlayerSystem` 可能撞上 ≤1 帧，且放置失败不扣物品。**不是缺陷**。
- **B13 同位置可双实例**【**第二轮撤销，第三轮部分恢复**】：`chunkExist:809-835` 已依次查 `activeChunks`/加载任务/`_loadChunks`/卸载任务/`_unloadChunks`，`addChunk` 前 `:159-167` 还有一次去重（注释"量子幽灵线程"）⇒ 异步主路径不会双实例。但 `loadChunkBlocking:861-865` 只查 `getChunk`（仅 `activeChunks`），随后 `initChunk:851-854`→`ChunkLoadTask.call()` 直接解码/生成并 `addChunk`，**不查 `chunkLoadingTasks`/`_loadChunks`**；唯一运行期调用点是复活（`PlayerSystem.java:322-329` → `:326`）。此时同名区块可能正在异步加载或已排队 ⇒ 两个同坐标 `Chunk` 同时进 `activeChunks`，`blockInstances`（键 `id@hashCode`）出现两套实例，卸载只摘一个。概率低但可达，记为 `N8` 的现实边界。
- **B14 装卸阈值无滞回 + 参考点不一致**【`【新】`，**第二轮降级为"轻微"**】：加载用 `player.getCenterPos()`（`:667`）、卸载用 `player.getX()/getY()`（`:695`），两者只差半格，阈值同为 `16 × PLAYER_VISUAL_RANGE`，且 `:670` 已有 `// TODO 实现更好的循环`——抖动带很窄，属已知粗糙而非结构性缺陷。
- **B15 容错策略相反**【S3】: `removeBlockInstance` 对 `BlockWithEntity` 缺键静默返回 null（`:447-449`），对普通方块抛 `IllegalArgumentException`（`:453-455`）；`removeBlockEntity` 同样静默。建议统一为"缺键 = 编程错误 → 抛"（附着物可保留容错，理由写清）。
- **B16 `placeAttachment` 不检查同格墙体**【`【新】`，**第二轮降级 🟢**】：生成器 `MainWorldChunkGenerator:84-85` 明确"附着物必须排在墙体遍历之后……跳过有墙体的格子"，玩家侧缺同一检查 ⇒ 规则不一致（能种进墙里），不崩不丢数据。
- **B17 `destroyBlock` 不碰墙体 → 悬空墙**【`【新】`，**第二轮改判"待维护者拍板"**】：`placeWall:512-513`"空气/水不得放墙"暗示墙需要固体垫底，而 `destroyBlock`（`:493-495`）只 `placeBlock(ARI)`。墙究竟是"独立图层"还是"依附方块"，代码与注释都未表态——**先问设计，别先改代码**。
- **B18 `removeBlock:320` 是死代码**【`【新】`】：零调用，且重复 `placeBlock` 的掉落/音效/粒子流程。
- **B19 坐标取整不一致**【**第二轮降级"待确认"**】：`getChunkPos:980-982` 是"先 `fastRound` 再 `floor(/16)`"，`:989` 有维护者封板注释 `///这里就该这么写，最好别动`；`wetlandStrength:1122`、`getBiomeAt:1139` 直接把未取整的世界坐标传进 `getChunkPosition`，块边界 0.5 格内可能取到邻块群系。与既有坐标约定一致，改之前先问。

### 3.6 方块与附着物（`world/block/`、`registry/Blocks`、`AttachmentPlacements`）

**职责**：方块原型与每格实例、方块实体、墙体、附着物、放置规则。

**优点**
- 原型/实例分离彻底：普通方块共享实例（省内存），`BlockWithEntity`/作物每格独享（有状态），用 `createSelf()`/`createInstance()` 一个方法表达，不需要两套类型。
- 放置规则外置成注册表，且"每个附着物只能注册一种方案（白/黑名单）"从结构上防冲突——这是我见过的同类设计里最干净的一种。
- `Blocks.READY` + `AttachmentPlacements.init()` 的顺序哨兵，把"静态初始化顺序"这个隐形炸弹显性化了。

**不足**

### 3.7 实体与玩家（`world/entity/`）

**职责**：实体基类、生命/背包/装备、状态效果、击退、寻路、玩家、敌人、子弹、物品实体、粒子。

**优点**
- `Entity` 只做身份与碰撞箱，位置推进/碰撞/渲染全部下沉到系统——单一职责做得比多数 libGDX 项目干净。
- `LivingEntity.update` 的顺序是经过推敲的：效果倒计时 → 背包 → attacked → 效果 tick → 击退 → 状态机（非击退才跑）→ 挥手。击退期间跳过状态机是正确取舍。

**不足**
- **B20 玩家防御计时器从不在防御开始时 reset**【`【新】`，高价值】：`Player.java:52-62` 两个计时器的 task 分别置 `isDefend=true/false`，但 `update` 里 `if (!isDefend) defendCDTimer.update(delta); else if (defendDurationTimer.isReady()) {} else defendDurationTimer.update(delta);`——`defendCDTimer` 到期自动把 `isDefend=true`，而 `defendDurationTimer` 在第一次防御后就被 `isReady()` 归零，**第二次防御只持续 1 帧**。空 `if` 分支正是掩盖它的地方（原清单疑点 `P-D*` 可升级为实缺陷）。

### 3.16 生成 / 寻路 / 粒子（简评）

- **生成**：`MonsterGenerationSystem`、`UndergroundCreatureGenSystem` 挂在世界尾部（§1.4）；`F-M3`（`setMaxGenSpan` 无效，`:102-104` 只改字段不重建 `genTimer`）仍成立；另有冷却冻结（提前 return 不计时）、单次 run 越限、落点校验不可见、`:95` 刷怪日志残留（`N22`~`N24`）；地下系统的 `maxCount`/`maxGenSpan` **连 setter 都没有**，外部无法配置。
- **寻路**：链为 `ChunkSystem` 改墙 → `PathfindingSystem.onWallChanged:121-128` 置 `dirty`、`wallVersion++` → `update:69-95`（目标位移 ≥1 格 或 `dirty` → `rebuildFlowField:103-116`；否则 `TaskTimer` 0.4s 触发）→ `FlowField.build:72`（缓存 4×4 区块 → 基础可走性 → 墙膨胀 → 从目标反向 BFS 写 `cost`/`dirIndex`）→ 消费 `getFlowDirection:141-144` → `FlowField.getDirection:215-223` 的 O(1) 查表。优点：一次构建全员共享，构建期零分配（数组队列 + 区块缓存 `:88-95`）。不足：`FlowField.java:183-185` **用 `lx / 16` 当区块下标**，而 `origin.x = floor(targetX) - 32` 通常不是 16 的倍数（对齐算法见 `isWalkableBase:199-200` 的 `floor(wx/16) - floor(origin.x/16)`）⇒ 墙体查到相邻区块的数组，膨胀漏标，贴身时碰撞箱可能嵌墙（`N25`）；`PathfindingSystem:92-93` 丢弃 `isReady()` 返回值、`dirty` 分支重建后不重置 `rebuildTimer`，全量 4096 格 + 膨胀可能相邻两帧各跑一次。**复核后否定的"缺陷"**：`getAwayDirection:241-252` 只比 `cost` 不查 `walkable`——BFS 在 `:160`/`:162-166` 已保证 `cost >= 0` 的格子必然可走且不穿角，因此这是安全的；`P-D6`（`cost` 为 `byte`）当前 `SIZE=64` 最多 63 步，触发不了。
- **粒子**：`ParticleSystem` + `PARTICLE(400)` 处理器；着色器侧 `F-C4`（uniform 无生产者）/`F-C5`（顶点色乘两次）属死代码与视觉偏差。

## 7. 结语

这个项目的**设计意图是清晰的**：注册即身份、系统串行、两条时间轴、异步区块、池化复用、事件解耦——六个机制互相支撑，读一遍入口（`FightCore` → `MainGameScreen` → `MainWorld`）加一遍 `ChunkSystem`，就能把 533 个文件的行为串起来。代码里大量注释写的是"**为什么**"（如 `removeChunk` 为什么要 `dropItems=false`、`ChunkLoadTask` 为什么要查中断），而不是"做了什么"，这是它能被读懂的关键。

**最大的风险不在设计，而在三处"边界纪律"的松动**：生成线程越界（S1）、读档失败降级（S2）、容错策略不统一（S3）。这三条不修，后面每加一个"每格实例"的功能（新作物、新方块实体、新附着物）都会再踩一次同类的坑——历史上 `P-B10`（读档植物不生长）就是 S3 的产物。

**建议**：先按 §5 的 A0/A/B 三批把"会崩/会丢数据/会静默失败"的口子堵上，再动 S1；随后把 §4.3 的 25 条（第二轮撤销 2、降级/改判 6，见 §4.5）按"是否影响玩家"分流，玩家可见的（`N3`、`N6`、`N11`、`N19`、`N25`）进下一个迭代，`N7` 等维护者拍板，其余进清理批次。每批改完同步三份文档，保持"清单是唯一真相"的现状。
