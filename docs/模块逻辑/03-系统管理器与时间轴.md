# 03 系统管理器与时间轴

> 覆盖：`SystemManager`、`GameSystemManager`、`WorldSystemsManager`、`TimeSystem`、`TaskTimer`、`Timer`。
> 一句话职责：**用“添加顺序”同时定义初始化顺序、每帧更新顺序和销毁顺序；再用两条互不干扰的时间轴（每帧 `update` / 固定 20Hz `tick`）把“表现”和“世界时间”分开**。

## 1. 职责与边界

| 做 | 不做 |
|---|---|
| 按添加顺序串行执行所有系统 | 系统内部的逻辑（各自实现） |
| 区分全局系统（GUI/输入/音频）与世界系统 | 决定系统之间的数据依赖（靠约定与顺序） |
| 提供“逻辑 tick”时钟与游戏内时间（`GAME_TIME`） | 渲染插值（渲染直接用 `delta`，§09） |
| 延迟增删 tick 对象（避免遍历中改集合） | 实体的每帧移动（在 `EntitySystem`，§07） |

## 2. 关键类型

| 类型 | 位置 | 说明 |
|---|---|---|
| `SystemManager` | `core/src/main/java/ttk/muxiuesd/system/abs/SystemManager.java` | 104 行；两张 `LinkedHashMap`（类→名字、名字→系统），保证顺序 |
| `GameSystemManager` | `.../system/manager/GameSystemManager.java` | 全局系统管理器（`FightCore` 持有），与屏幕无关 |
| `WorldSystemsManager` | `.../system/manager/WorldSystemsManager.java` | 世界系统管理器（`World` 持有），每局一份 |
| `TimeSystem` | `.../system/TimeSystem.java` | 117 行；游戏内时间 + 20Hz tick 驱动 |
| `TaskTimer` / `Timer` | `core/src/main/java/game/muxiuesd/bedrockcore/util/` | 倒计时/周期任务，`isReady()` 会“跑到点就执行并归零” |

## 3. 管理器逻辑链

```
addSystem(system)                          [SystemManager.java:29-51]
 ├─ 名字 = system.getClass().getName()（或显式名）
 ├─ 若已存在同名：
 │    ├─ 旧系统若是 IRenderTask → removeSystemRenderTask(?)   ← 这里有 bug，见 §8
 │    └─ 覆盖映射
 └─ put(clazz→name), put(name→system)

initAllSystems()                           [:75-80] 按插入顺序 forEach → initialize()
update(delta)                              [:96-98] 按插入顺序 forEach → update(delta)
dispose()                                  [:101-103] 按插入顺序 forEach → Disposable.dispose()
```

**顺序即契约**：

- 初始化顺序：`TimeSystem → EventSystem → PlayerSystem → ChunkSystem → ChunkRenderSystem → PathfindingSystem → EntitySystem → … → WorldInputHandleSystem → … → LightSystem`（`MainWorld.java:20-41`）。
- 因为 `ChunkSystem.initialize()` 需要 `PlayerSystem` 已初始化、`EntitySystem.initialize()` 需要 `TimeSystem`，**这个顺序不能随便调**（调了会在 `initialize` 里 NPE）。
- 每帧顺序决定了“谁能看到谁本帧的修改”：`PlayerSystem` 在 `ChunkSystem` 之前，所以玩家输入产生的放置请求会作用于本帧已经存在的区块（在途区块不可见，`D2`）。

## 4. 时间轴逻辑链

```
TimeSystem.update(delta)                   [TimeSystem.java:42-66]
 ├─ 合并 _delayAdd → tickUpdates            （遍历中增删的安全副本）
 ├─ 处理 _delayRemove
 ├─ gameTime += delta * 10f / 60f           （1 现实秒 = 10 游戏分钟）
 ├─ if (gameTime >= 24) gameTime -= 24
 └─ if (tickSpan >= TickMaxSpan) { tick(world, tickSpan); tickSpan = 0; }
    else tickSpan += delta;                ← 注意：不是“固定步长累加”，是“够长就跑一次”
```

`tick()`：遍历 `tickUpdates` 逐个 `tick()`，然后 `EventBus.post(EventTypes.WORLD_TICK, ...)`。

**两条时间轴的用法**：

| 轴 | 频率 | 用来做 | 典型实现 |
|---|---|---|---|
| `update(delta)` | 每帧、变步长 | 物理、输入、相机、动画、UI | `Updateable` |
| `tick()` | ~20Hz | 生长、烧炼、刷怪、寻路重建 | `Tickable` + `TimeSystem.add/remove` |

**判定**：需要“与帧率无关的固定节奏” → `Tickable`；需要“每帧都顺滑” → `Updateable`。两者都实现的对象（如 `BlockEntity`）分别在两条链上被驱动。

## 5. 游戏内时间

| 方法 | 区间 | 备注 |
|---|---|---|
| `isDay()` | `gameTime > 0 && <= 9.6` | **0 点整不算白天**（`B8`，一帧边界） |
| `isDusk()` | `(9.6, 14.4]` | 黄昏 |
| `isNight()` | `(14.4, 24]` | 夜晚，刷怪只在这段（§13） |

`GAME_TIME` 存在 `WorldInfoTypes.FLOAT`：构造时 `putIfNull` 再读出，`dispose()` 写回——所以时间随存档走，但**不写进 `world.json` 的字段**，而是共享的 `WorldInfoTypes`。

## 6. 与其他模块的联动

| 方向 | 对象 | 交接内容 |
|---|---|---|
| 上游 | §01 启动 | `FightCore` 建 `GameSystemManager` 并注册 3 个全局系统；`MainGameScreen` 建 `WorldSystemsManager` |
| 下游 | 全部世界系统 | 每个系统实现 `GameSystem`（`initialize/update/dispose`） |
| 下游 | §05 区块 | `ChunkSystem.update` 是区块装卸的唯一驱动 |
| 下游 | §06 方块 | `addBlockInstance` 把 `Tickable` 方块塞进 `TimeSystem.tickUpdates` |
| 下游 | §07 实体 | `EntitySystem` 用 `TimeSystem` 的 tick 跑 AI/碰撞 |
| 下游 | §13 生成/寻路 | 刷怪与流场重建都用 `TaskTimer`（不是 `TimeSystem`），但只在 `update` 里推进 |

## 7. 刻意设计与代价

- **顺序即契约**（`LinkedHashMap`）：不引入依赖注入/拓扑排序，靠“注册顺序”表达依赖，简单可读。代价：调换顺序会静默改变行为，且在 `initialize` 里才炸。
- **tick 用“累积够长就跑一次”**：实现简单、无需固定步长累加器；代价是大 `delta`（卡顿/断点）只补一次 tick，时间被压缩，余数丢弃（`D11`）。
- **`getSystem(Class)` 返 null（`D12`）**：让“可选系统”（如寻路）可以缺省；代价是与 `getSystem(String)` 抛异常不一致，调用方只能到处判空。

## 9. 改动指引

- 新增系统：实现 `GameSystem`，在 `MainWorld.addAllSystems()` 或 `FightCore` 注册；**放在正确的位置**（依赖谁就排在谁后面）。
- 新增周期性逻辑：优先 `TaskTimer`（自己 `update`），需要“世界时间”才用 `TimeSystem.add`。
- 改 tick 频率：只改 `TickMaxSpan`，但要意识到所有 `Tickable` 的节奏会一起变。
